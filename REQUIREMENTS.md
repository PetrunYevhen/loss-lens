# Daily Production Metrics Dashboard: MVP Requirements

Status: Draft v0.1
Domain: EMS (Electronics Manufacturing Services), SMT/test lines
Stack: Angular + TypeScript (frontend), ASP.NET Core / C# (backend)
Data: mock, generated by the backend (real data is a later step)

---

## 1. Purpose and scope

A web app that shows **daily production metrics** for an electronics assembly plant so that operators, line supervisors and managers can see how the day is going and where the problems are.

The MVP covers three metric groups: **plan attainment**, **First Pass Yield (FPY)** and **defect analysis**. Data is generated by the backend. The data source must be replaceable with a real one later without changing the API contract (see 6 and 8).

### 1.1 In scope (MVP)
- Dashboard with KPI cards (plan attainment, FPY, DPMO, top defect).
- Plan vs actual by hour.
- FPY trend and FPY by station.
- Defect Pareto and DPMO.
- Filters: date, line, shift.
- Three roles with different data scope (demo role selector, see 3).
- Deterministic mock data generator.

### 1.2 Out of scope (MVP)
- Real data sources, real authentication.
- Smartwatch / push notifications (see open question Q1).
- OEE, downtime analysis, export to CSV/PDF, admin UI, multi-site.

### 1.3 Open questions and working assumptions
Assumptions are marked so they can be confirmed with the people who gave the task. Keep them configurable, do not hard-code.

| # | Question | Working assumption |
|---|---|---|
| Q1 | Smartwatch: is the watch the manufactured product, or a device for alerts? | Not in MVP. If alerts: 1-3 numbers plus a push when a threshold is breached. |
| Q2 | What is the real data source (MES DB, CSV, API)? | Mock now, behind `IMetricsRepository`. |

## 2. Glossary

- **EMS**: Electronics Manufacturing Services, contract manufacturer of electronics for OEM brands.
- **SMT**: Surface Mount Technology (component placement on PCBs).
- **AOI / SPI / ICT / FCT**: automated optical inspection / solder paste inspection / in-circuit test / functional test (stations on the line).
- **Plan attainment**: share of the planned output that was actually produced as good units.
- **FPY**: First Pass Yield, share of units that pass a test at the first attempt (no rework or retest).
- **RTY**: Rolled Throughput Yield, the product of FPYs across stations.
- **DPMO**: Defects Per Million Opportunities.
- **Pareto**: defect causes sorted descending with a cumulative percentage.
- **RAG**: Red / Amber / Green status.

## 3. Users and roles

| Role | Needs | Data scope |
|---|---|---|
| Operator | Current shift: plan vs actual per hour, defects of own line | Own line, own shift, read-only |
| Line Supervisor | FPY by station, defect Pareto, trend | Assigned lines (one or more) |
| Manager | Daily summary of all lines, comparison, trends | All lines |

**MVP authentication (demo only).** The user picks a role (and a line for Operator/Supervisor) in a role selector. The frontend sends `X-Demo-Role` and `X-Demo-LineIds` headers, the backend enforces the scope. This is **not secure** and must be replaced by JWT with roles later (see 11). Out-of-scope data returns `403`.

## 4. Metric definitions

All metrics are calculated **in the backend only**. The frontend never recomputes them. Calculators are pure functions with no I/O.

### 4.1 Plan attainment
```
planAttainment = goodUnits / plannedUnits * 100
```
- `goodUnits`: units that passed the final test in the period.
- `plannedUnits == 0` -> value is `null` (UI shows "-").
- The value may exceed 100%, show it as is.

### 4.2 First Pass Yield
```
stationFPY = firstPassUnits / testedUnits * 100
lineRTY    = product of stationFPY/100 for all test stations of the line * 100
```
- `testedUnits` counts units tested for the **first time** at the station. Retests after repair are excluded.
- `testedUnits == 0` -> `null`. A `null` station is skipped in RTY, and the response flags `incomplete: true`.

### 4.3 Defects
```
DPMO = defectCount / (unitsInspected * opportunitiesPerUnit) * 1_000_000
```
- `unitsInspected == 0` -> `null`.
- Pareto: defect codes sorted by count descending, each with `share` and `cumulativeShare`. Codes after 95% cumulative may be grouped as "Other" (UI option).

### 4.4 RAG thresholds (placeholders in `appsettings.json`)
| Metric | Green | Amber | Red |
|---|---|---|---|
| Plan attainment | >= 95 | >= 85 | < 85 |
| Line FPY (RTY) | >= 92 | >= 88 | < 88 |
| Station FPY | >= 97 | >= 94 | < 94 |

`null` values have status `unknown` (grey).

### 4.5 Rounding
The API returns full precision. The UI shows 1 decimal for percentages and integers for DPMO.

## 5. Functional requirements

### 5.1 Common
- **FR-CMN-1**: Filters: date (default today), line, shift (A/B/C/All). The role limits the allowed lines.
- **FR-CMN-2**: Filters are reflected in URL query params, so a view can be shared.
- **FR-CMN-3**: Every data view has loading, empty and error states (with a retry button).
- **FR-CMN-4**: Optional auto-refresh every 60 seconds (toggle, off by default).
- **FR-CMN-5**: Status is never conveyed by color alone (also icon and text).

### 5.2 Dashboard
- **FR-DSH-1**: KPI cards: Plan attainment, Line FPY (RTY), DPMO, top defect.
- **FR-DSH-2**: Each card shows value, target (from thresholds), RAG status and delta vs previous day.
- **FR-DSH-3**: A card click opens the related detail view with the same filters.

### 5.3 Plan vs actual
- **FR-PLN-1**: Hourly chart for the selected date: planned vs good units (bars) and cumulative actual (line).
- **FR-PLN-2**: Table with the same data. Hours that have not started yet have no actual value.

### 5.4 FPY
- **FR-FPY-1**: Trend chart over 7 / 14 / 30 days (selectable) for the line FPY.
- **FR-FPY-2**: Bar chart of FPY by station for the selected date/shift with RAG colors.
- **FR-FPY-3**: Clicking a station opens the defect view filtered to that station.

### 5.5 Defect analysis
- **FR-DEF-1**: Pareto chart (bars plus cumulative line) for the selected period.
- **FR-DEF-2**: Filter by station. Table with code, name, count, share, cumulative share.
- **FR-DEF-3**: DPMO for the selected scope.

### 5.6 Mock data
- **FR-DAT-1**: Generator is deterministic (fixed seed, same data on every start).
- **FR-DAT-2**: 30 days of history, 3 lines, stations per line: SPI, AOI, ICT, FCT, 3 shifts.
- **FR-DAT-3**: Realistic ranges: 80-120 planned units per line per hour, station FPY 94-99.5%.
- **FR-DAT-4**: Pareto-like defect distribution (a few causes dominate): e.g. solder bridge, insufficient solder, missing component, tombstone, wrong polarity.
- **FR-DAT-5**: Planted anomalies so charts show something: one shift with low FPY, one line with an hour of near-zero output.
- **FR-DAT-6**: For "today", data exists only up to the current hour (Europe/Kyiv).
- **FR-DAT-7**: Access only through `IMetricsRepository`. `MockMetricsRepository` is one implementation.

## 6. API contract (REST, JSON)

Base path `/api/v1`. Dates `yyyy-MM-dd`, timestamps ISO 8601. Errors use RFC 7807 `ProblemDetails`.

| Endpoint | Query params | Returns |
|---|---|---|
| `GET /lines` | none | lines the role may see, with stations |
| `GET /kpi/summary` | `date`, `lineId?`, `shiftId?` | KPI values, targets, RAG, delta vs previous day |
| `GET /plan-vs-actual` | `date`, `lineId`, `shiftId?` | array of `{hour, planned, good}` |
| `GET /fpy/trend` | `from`, `to`, `lineId?` | array of `{date, rty}` |
| `GET /fpy/stations` | `date`, `lineId`, `shiftId?` | array of `{stationId, name, tested, firstPass, fpy, status}` |
| `GET /defects/pareto` | `from`, `to`, `lineId?`, `stationId?`, `shiftId?` | `{items:[{code,name,count,share,cumulativeShare}], dpmo}` |
| `GET /config/thresholds` | none | current thresholds |

Example `GET /kpi/summary`:
```json
{
  "date": "2026-11-11",
  "planAttainment": { "value": 92.0, "target": 95, "status": "amber", "deltaVsPrevDay": -1.5 },
  "lineRty":        { "value": 90.3, "target": 92, "status": "amber", "deltaVsPrevDay": 0.4, "incomplete": false },
  "dpmo":           { "value": 120 },
  "topDefect":      { "code": "SB", "name": "Solder bridge", "count": 48 }
}
```

Validation: `from <= to`, range max 90 days, unknown `lineId` -> `404`, out-of-scope -> `403`, malformed params -> `400` with field details.

## 7. Data model (backend entities)

- **ProductionLine** `{ id, name }`
- **Station** `{ id, lineId, name, type: SPI|AOI|ICT|FCT, order }`
- **Shift** `{ id, name, start, end }`
- **HourlyRecord** `{ date, hour, lineId, shiftId, plannedUnits, goodUnits }`
- **TestRecord** `{ date, hour, stationId, testedUnits, firstPassUnits }`
- **DefectCode** `{ code, name, category }`
- **DefectEntry** `{ date, hour, stationId, defectCode, count }`
- Config: `opportunitiesPerUnit`, thresholds.

Business rule: `firstPassUnits <= testedUnits`, `goodUnits >= 0`, defects are linked to a station.

## 8. Non-functional requirements and architecture

**Backend (C#, ASP.NET Core, current .NET LTS)**
- Layers: `Api` (thin controllers) -> `Core` (metric calculators, pure functions) -> `Infrastructure` (mock repository behind `IMetricsRepository`).
- Nullable reference types on, warnings as errors for analyzers where practical.
- OpenAPI/Swagger, health endpoint, structured logging, CORS limited to the dev origin.
- No database in MVP (in-memory mock). EF Core can be added later behind the same interface.

**Frontend (Angular, TypeScript strict)**
- Standalone components, signals for state, feature folders: `dashboard`, `plan`, `fpy`, `defects`, `shared`.
- Typed API client services, DTO interfaces mirror section 6.
- Charts: Apache ECharts via `ngx-echarts` (supports bar+line combo for Pareto). Replaceable.
- No NgRx in MVP.

**Quality**
- xUnit tests for all formulas including edge cases (zero division, nulls, incomplete stations).
- Integration tests (`WebApplicationFactory`) for each endpoint, incl. role scope (`403`).
- Frontend component tests for the KPI card and RAG logic.

**UX / performance**
- Responsive from 360 px (phone, shop-floor tablet) to 1920 px (wall display).
- Accessible: contrast, keyboard navigation, not color-only status.
- Number/date format `uk-UA`. Strings in a resource file.
- Each endpoint responds within 300 ms on mock data, dashboard loads within 2 s.

**Security (MVP)**
- Demo auth only (see 3). No secrets in the repo. Validate all inputs.

## 9. Acceptance criteria (testable examples)

- **AC-1** Plan attainment: planned 100, good 92 -> `92.0`, status `amber`.
- **AC-2** Plan attainment: planned 0 -> `null`, UI shows "-".
- **AC-3** RTY: station FPYs 98%, 96%, 97%, 99% -> `90.3%`.
- **AC-4** DPMO: 12 defects, 500 units, 200 opportunities -> `120`.
- **AC-5** Pareto: counts 50, 30, 15, 5 -> cumulative `50, 80, 95, 100`%.
- **AC-6** A station with `testedUnits = 0` is skipped in RTY and the response has `incomplete: true`.
- **AC-7** Operator of line 1 requesting line 2 data gets `403`.
- **AC-8** Changing filters updates the URL, and opening that URL restores the same view.
- **AC-9** Same seed produces identical mock data across restarts.
